# ADR 0007 — нейтральная внутренняя база вместо мини-agora

**Дата:** 2026-11-03 · **Статус:** принято · **Этап:** 6

## Контекст

Внутренняя база создавалась как копия контракта `agora`: `TemplateVault` клал в jar пять файлов
`40_Knowledge/_meta/*` (CONTRACT.md, STRUCTURE.md, taxonomy.yaml, шаблоны заметок), а
`NoteRenderer` строил путь по словарю тем (`<domain>/<topic>`), прогонял линтер `agora_lint.py`
и требовал обязательный `domain` во frontmatter.

Это обслуживает один сценарий — «писать сразу в базу, совместимую с agora», — и навязывает его
всем пользователям. У пользователя может не быть ни agora, ни `taxonomy.yaml`, ни Obsidian в
нашем понимании; контракт, линтер и словарь превращаются в требования, которые он не просил.
Плата за это: шаблон в jar, копия линтера в поде (ConfigMap), зависимость рендера от таксономии,
жёсткий отказ записи при несоответствии контракту.

## Решения

1. **Два вида базы с разными обязательствами.**
   - `INTERNAL_DIR` — нейтральное хранилище сервиса: `notes/<Topic>/<Name>.md`, без контракта,
     словаря, линтера и `_Inbox`. Пользователь забирает содержимое через `/export` и
     распоряжается им сам.
   - `EXTERNAL_OBSIDIAN` — база пользователя с контрактом (наша agora, если он её подключил):
     словарь тем, `_meta/CONTRACT.md`, линтер, `_Inbox`. Всё это остаётся как было.

2. **Внутренняя база — плоский нейтральный формат.** Путь `notes/<TopicSlug>/<Name>.md`,
   тема — свободный текст от модели в frontmatter, а не каталог домена:

   ```yaml
   ---
   type: concept
   topic: "Kafka Streams"
   status: raw
   source: telegram
   id: 0192f3c4-...
   created: 2026-11-03
   updated: 2026-11-03
   summary: "одно предложение до 150 символов"
   ---
   ```

   `domain` не пишется: он принадлежит контракту agora и вычисляется при импорте.
   Поле `tags` не добавляется: модель не отдаёт ключевых слов, а пустой список — шум.

3. **Удаляются `TemplateVault` и ресурсы `vault-template/`.** Вместо них `PlainVault` создаёт
   `<root>/notes/` с правами 700. `README.md` с описанием формата кладётся в **архив** при
   экспорте, а не в каталог пользователя: выгрузка самоописательная, каталог — чистый.

4. **Линтер и `ContractValidator` работают только для внешней базы.** Для внутренней остаются
   проверки, не зависящие от контракта: непустые `title`/`topic`/`summary`, `confidence` в 0..1,
   санитайз тела, имя файла по `FileNamePolicy`, уникальность по всей базе.

5. **Экспорт (`/export`) — единственный путь наружу для внутренней базы.** Архив содержит
   `notes/**` и `README.md`; валидатор контракта в него больше не входит (файлы не претендуют
   на соответствие agora). Для внешней базы `/export` по-прежнему отвечает отказом: её файлы
   уже лежат у пользователя.

6. **Импорт в agora — снаружи сервиса.** Выгрузка разбирается скриптом: тема из frontmatter →
   `domain/topic` по `taxonomy.yaml` → заметка в `40_Knowledge/` → `agora_lint.py`. Для этого
   в формате сохраняются `topic` и `summary`; больше ничего сервис не обещает.

## Последствия

- Пользователь больше не получает базу «под agora» по умолчанию; сценарий «сразу в agora»
  остаётся через подключение внешней базы (это путь владельца).
- Проверок при записи меньше: битые вики-ссылки и абсолютные пути во внутренней базе не
  отсекаются контрактом. Остаются санитайз и обязательные поля. Пользователь получает сырьё,
  а не релиз.
- `taxonomy` для внутренней базы — пустой (`Taxonomy.free()`), промпт DRAFT получает
  `taxonomy_mode: free` и генерирует тему свободным текстом (промпт v2).
- Миграция БД `V3`: `taxonomy_relpath`/`inbox_relpath` становятся nullable, мёртвые колонки
  `git_remote`/`branch` удаляются.
- Слияние двух баз в одну (импорт выгрузки в agora) — задача агента, а не сервиса: у неё нет
  и не должно быть знания о раскладке `40_Knowledge` сверх контракта.
