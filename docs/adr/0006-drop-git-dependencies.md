# ADR 0006 — отказ от git-зависимостей в записи

**Дата:** 2026-11-03 · **Статус:** принято · **Этап:** 6

## Контекст

Сервис никогда не делал git-операций (v1.2, JGit удалён), но продолжал читать git как источник
данных: `GitIndex` вызывал `git ls-files` для проверки уникальности имён, `ContractValidator`
требовал строку `.uzelok-tmp/` в `.gitignore` и проверял наличие `git --version`,
`DirVaultStore` ждал исчезновения `.git/index.lock` перед записью, а вид базы при подключении
определялся наличием каталога `.git`.

В прод-образе (`eclipse-temurin:25-jre-noble` + python3 и PyYAML) бинарника git нет, а внешняя
база владельца (`/mnt/hdd/workspace/agora`) смонтирована через hostPath — с `.git`. Следствия,
наблюдаемые на живом боте:

- на каждом превью заметки висит предупреждение «git недоступен, проверка индекса базы пропущена»,
  потому что `ContractValidator.warnings` попадают в `PreparedNote` и в сообщение;
- объединение «`Files.walk` ∪ `git ls-files`» в поде вырождается в чистый обход ФС — то есть
  git-ветка не работает, а её отказы (таймаут 5 с, пустой индекс при ошибке) маскируются;
- запись откладывается на 10 с и падает `ContractViolation`, если пользователь в этот момент
  коммитит свою базу (`.git/index.lock`);
- внешняя Obsidian-база без git (папка на Syncthing/Dropbox) получает `kind = INTERNAL_DIR`,
  после чего бот по ошибке предлагает для неё `/export` и не проверяет контракт так, как должен.

## Решения

1. **Удалить `GitIndex`.** Источник правды о существующих файлах — файловая система
   (`Files.walk`). Индекс git знает о файлах, удалённых из рабочего дерева, но не знает о
   неотслеживаемых — оба расхождения с диском дают ложные решения. После удаления имя,
   освободившееся при удалении заметки, доступно сразу.

2. **`ContractValidator` не смотрит на git.** Убираются проверка `.gitignore` и `gitAvailable()`,
   предупреждение о git исчезает из превью.

3. **Убрать ожидание `.git/index.lock`.** Взаимное исключение записей держит
   `VaultLockRegistry` (ReentrantLock по `knowledge_base.id`), этого достаточно при `replicas: 1`.
   Чужая синхронизация не должна превращаться в отказ нашей записи: `Files.move(ATOMIC_MOVE)`
   атомарен по отношению к читателям, а конфликт содержимого ловится хешем.

4. **Вид базы — из способа её создания**, а не из файловой системы: `createInternal` →
   `INTERNAL_DIR`, `connect` → `EXTERNAL_OBSIDIAN`. Колонка `kind` уже хранится в
   `knowledge_base`, поэтому бэкфилл не нужен: внутренних баз в проде нет
   (`/var/lib/uzelok/vaults` отсутствует), единственная база — внешняя Agora.

5. **Временный файл атомарной записи — рядом с целевым** (`<каталог>/.uzelok-tmp-<uuid>`),
   а не общим каталогом в корне базы. Требование к `.gitignore` и каталог `.uzelok-tmp/`
   из шаблона уходят; dot-файлы Obsidian в списке не показывает.

## Последствия

- Образ остаётся без git; из окружения уходит неявная зависимость на бинарник.
- На внешней базе больше нет предупреждений и пауз, связанных с git, но и защиты от гонки с
  внешним `git add` нет: последний пишущий побеждает. Для MVP с одним подом и ручной
  синхронизацией это приемлемо.
- Удалённые в базе заметки больше не держат имя: повторная генерация с тем же заголовком
  займёт освободившееся имя, а не уйдёт в `_Inbox` с суффиксом.
- `note_version` остаётся единственной историей версий: git-история заметки сервису не видна
  и не нужна.
