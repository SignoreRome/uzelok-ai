# ADR 0003: отказ от Spring AI, LLM — собственный HTTP-клиент

**Статус:** принято (этап 3, часть 3a).

Зависимость `spring-ai-starter-model-openai` удалена из сборки. Взаимодействие с LLM во второй части этапа 3
(3b) реализуется собственным HTTP-клиентом над OpenAI-совместимым API: `base-url`, `api-key`, `model` и
`response_format` берутся из `uzelok.llm` (там уже описаны `providers` и `steps`).

Причины, проверенные на живом контексте:

- Стартер поднимает **все** автоконфигурации OpenAI-моделей (chat, audio speech, embedding, moderation) и
  валит старт приложения без ключа: `OpenAiAudioSpeechAutoConfiguration` →
  `At least one credential source must be specified`. Проверено запуском `java -jar` с реальной БД:
  контекст падал, сервис не стартовал. Отключать по одной автоконфигурации через
  `spring.ai.model.*=none` — хрупко: набор моделей меняется от версии к версии.
- У нас не один провайдер, а два (`openrouter`, `opencode-go`) и выбор модели **по шагу**, из конфига.
  Автоконфигурация Spring AI рассчитана на один `ChatModel` на контекст; маршрутизация по шагам
  превращалась бы в ручную сборку нескольких бинов поверх автоконфигурации.
- Нужен точный учёт: `usage` из ответа, стоимость вызова в `llm_call`, `request_key` для идемпотентности,
  жёсткая проверка `response_format: json_schema`. Собственный клиент даёт это напрямую, без адаптеров.
- Тестируемость: клиент проверяется фейковым HTTP-сервером (`com.sun.net.httpserver`) без Spring-контекста
  и без сетевых моков библиотеки.

Цена решения: парсинг ответа и схемы — наш код; при смене API провайдера правим один класс. Spring AI
вернётся в проект только если понадобятся его возможности (tools, advisors, векторные хранилища), и тогда —
с явным отключением ненужных автоконфигураций и проверкой старта в CI.

Побочный эффект: размер fat-jar уменьшился со 130 МБ до 25 МБ; из рантайма ушли лишние модели и SDK.
