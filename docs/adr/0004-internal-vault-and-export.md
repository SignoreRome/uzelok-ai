# ADR 0004 — внутренняя база знаний и экспорт архива

**Дата:** 2026-11-02 · **Статус:** принято · **Этап:** 4

## Контекст

MVP поддерживает два режима хранения: внешняя Obsidian-база (git-репозиторий пользователя) и
внутренняя, которую создаёт сервис (`KnowledgeBaseKind.INTERNAL_DIR`). Этап 2 реализовал только
внешнюю (`ExternalObsidianStore`), этап 3 — конвейер записи. Осталось: создать внутреннюю базу,
писать в неё и отдавать её пользователю архивом по `/export` (FR-24).

Вопросы, которые пришлось решить: где живут внутренние базы, чем внутренний store отличается от
внешнего, как хранить состояние диалога онбординга, как делить архив больше лимита Bot API.

## Решения

1. **Внутренние базы — `<uzelok.storage.vaults-dir>/<tenantId>`**, по умолчанию
   `/var/lib/uzelok/vaults` (тот же том, что артефакты, §13 ТЗ). Имя каталога — UUID тенанта:
   без транслитерации, без коллизий, без пользовательского ввода в пути. База создаётся из
   шаблона `src/main/resources/vault-template/` (копия `_meta` базы `agora`: `CONTRACT.md`,
   `STRUCTURE.md`, `taxonomy.yaml`, шаблоны заметок). Шаблон лежит в jar, поэтому копирование —
   явный список путей через `getResourceAsStream`, без сканирования classpath и без Spring.
   Пустые `_Inbox/` и `.uzelok-tmp/` создаются кодом.

2. **Внутренний store — тот же код, что внешний, с одним отличием.** Разница между режимами после
   отказа от JGit (v1.2) свелась к ожиданию `.git/index.lock` и к источнику списка имён; второе уже
   покрыто `NameUniqueness` (git-индекс пуст, если `.git` нет). Поэтому общая логика вынесена в
   `DirVaultStore` с хуком `gitAware()`, а `ExternalObsidianStore`/`InternalDirStore` — тонкие
   наследники. Дублировать 400 строк записи ради «чистого» разделения дороже, чем один флаг.

3. **Выбор стора — по `knowledge_base.kind`** (`KnowledgeStoreRouter`), а не по наличию `.git`:
   вид базы — это данные, записанные при онбординге, а не догадка по файловой системе.

4. **Состояние диалога «пришлите путь» — в БД** (`onboarding_session`, одна строка на чат, TTL 15 мин).
   In-memory карта потерялась бы при рестарте пода: пользователь остался бы без ответа на уже
   отправленный путь. Атомарное изъятие (`DELETE ... WHERE expires_at > now RETURNING`) исключает
   двойную обработку при повторной доставке апдейта.

5. **Подключение существующей базы проверяется тем же `ContractValidator`**, что и запись:
   наличие `40_Knowledge/_meta/taxonomy.yaml` и `CONTRACT.md`, `contract_version = 2`. Вид базы при
   подключении — по наличию `.git` (внутреннюю базу тоже можно «подключить» повторно).

6. **Экспорт — zip силами JDK** (`java.util.zip`), без новых зависимостей. Одна часть до
   `uzelok.knowledge.export-max-bytes` (50 МБ — лимит Bot API на документ); больше — жадное деление
   по 4/5 лимита и рекурсивное дробление части, если сжатие не помогло. Отправка — потоковая
   (`InputFile(File)`), чтобы не держать 50 МБ в heap при лимите пода 1536 MiB. Временные архивы
   удаляются в `finally`, даже если отправка упала.

## Последствия

- Внутренняя база — обычный каталог Obsidian-vault: её можно скачать `/export` и открыть локально;
  git-операций сервис не делает ни в одном режиме.
- Онбординг доступен только пользователю без базы; смена базы при уже подключённой — вне MVP
  (потребует миграции `note.knowledge_base_id` и явного сценария).
- Имя каталога внутренней базы — UUID; человекочитаемого имени у базы в MVP нет.
- `uzelok.storage.vaults-dir`/`exports-dir` должны попасть в PVC пода на этапе 5.
