# ТЗ: учёт LLM-расхода в Uzelok (этап 7), версия 2

**Изменения относительно v1:** приняты решения по разделу 9 (9.1–9.4); техническая поправка 2.1 переписана по фактам кода (в исходной формулировке ревью она описывала несуществующий сценарий); поправки 2.2 и 2.3 приняты с уточнениями.

**Статус:** утверждено к реализации. Объём — только учёт; маршрутизатор `PolicyDrivenLlmClient`, сетевой шлюз, eval и смена моделей остаются вне этапа.

---

## 1. Что делаем

Делаем расход LLM измеримым: фактическая модель, слот, причина фолбэка, кеш-токены, честная стоимость — в БД сервиса; сводный отчёт с дрейфом и юнит-экономикой — отдельным скриптом на хосте.

## 2. Решения по открытым вопросам (v1 §9)

- **9.1. Сырой вход в БД не хранить.** `response_text` остаётся как есть; промпты, OCR-текст и base64-изображения в PostgreSQL не пишутся. Фикстуры для будущего eval собираются в репозитории вручную либо отдельной утилитой выгрузки по `job_id`, пока не истёк TTL вложений (72 ч).
- **9.2. `allowance_pct_delta` считает только агрегатор.** Из миграции колонку **убираем**; месячные лимиты квот в `application.yml` **не заводим**. Причина: приложение это поле в рантайме не использует, а лимиты Go в конфиге стали бы вторым источником правды. Требование R6 переносится на Python-агрегатор.
- **9.3. Отчёт по расписанию + алерт только при аномалии.** Ежедневный запуск 07:00 НСК пишет полный отчёт в файл; сообщение в Telegram уходит только если (а) `|Drift| > 5 %`, (б) любое окно провайдера ≥ 80 %, (в) недоступен хотя бы один источник данных.
- **9.4. Порог Drift = 5 %.** `/v1/usage` отдаёт проценты целыми числами (±1 % округления), плюс пиковая тарификация DeepSeek — более узкий порог даст ложные срабатывания и обесценит алерт.

## 3. Поправки ревью — что принято, что уточнено по коду

### 3.1. Учёт сожжённых токенов при провале контракта

**Как было в ревью:** при `SCHEMA_INVALID` первая модель сжигает токены, строка перезаписывается результатом второй, расход теряется.

**Что в коде на самом деле** (`OpenAiCompatibleLlmGateway`):

- `request_key` включает модель (`step|tenant|input_hash|model|prompt_version|draftVersion|variant`, `LlmRequestKey.of`), поэтому каждая попытка с другой моделью получает **свой** ключ — перезаписи строк нет;
- при `LlmCallFailed` (429/таймаут/сеть) строка не пишется вообще, и это правильно: токены не списаны;
- при `LlmContractViolation` пишется строка `status='FAILED'` с реальными токенами и `response_text`, но **`cost_usd = 0`** — вот здесь расход теряется;
- фолбэка на резервную модель по нарушению контракта **нет**: `throw violation` сразу выходит из цикла.

**Решение для этапа 7:**

1. `recordFailure` считает стоимость по тем же токенам и той же формуле, что и успешный вызов (вместо `BigDecimal.ZERO`).
2. Фолбэк по контракту **не добавляем**: это изменение поведения конвейера (нужны свои тесты, решение «что считать валидным для второй попытки»), выносим отдельной задачей.
3. В отчёте FAILED-строки входят в общий расход — иначе дрейф будет расти на каждом провале валидатора.

### 3.2. Формула стоимости

Принято, с уточнением: слагаемое записи в кеш включаем в формулу, но у текущих провайдеров (`opencode-go`, `openrouter`) поле `cache_write_tokens` не приходит и остаётся `0`.

```
uncached_in = max(0, prompt_tokens - cache_read_tokens - cache_write_tokens)
cost = uncached_in × P_in + cache_read × P_cache_read + cache_write × P_cache_write + out × P_out
```

`max(0, …)` обязателен: провайдеры по-разному репортит `prompt_tokens` относительно кешированных.

### 3.3. Скользящие окна и `state.db`

Принято как риск. Факты: в `~/.hermes/state.db` есть таблица `messages` с `timestamp` и `token_count`, но без разбивки по моделям и кешу; расход по моделям лежит только в `session_model_usage` (агрегат на сессию, `first_seen`/`last_seen`).

**Решение для агрегатора:**

1. Основная метрика окна берётся у провайдера (`/v1/usage`).
2. Локальная сумма по Hermes для окон 5 ч и 7 дней считается с явной пометкой «оценка»: сессии, пересекающие границу окна, помечаются и не участвуют в алерте по дрейфу.
3. Каждый запуск сохраняет снапшот счётчиков `session_model_usage` в `~/.hermes/state/llm-usage-snapshots.json`; дельта между соседними снапшотами даёт точный расход за интервал между запусками (для дневного отчёта этого достаточно).

## 4. Объём работ

### 4.1. Миграция `V7__llm_accounting.sql`

```sql
ALTER TABLE llm_call
    ADD COLUMN IF NOT EXISTS slot text,
    ADD COLUMN IF NOT EXISTS requested_model text,
    ADD COLUMN IF NOT EXISTS fallback_reason text,
    ADD COLUMN IF NOT EXISTS cache_read_tokens int NOT NULL DEFAULT 0,
    ADD COLUMN IF NOT EXISTS cache_write_tokens int NOT NULL DEFAULT 0,
    ADD COLUMN IF NOT EXISTS reasoning_tokens int NOT NULL DEFAULT 0;

CREATE INDEX IF NOT EXISTS llm_call_created_idx ON llm_call (created_at);
CREATE INDEX IF NOT EXISTS llm_call_slot_created_idx ON llm_call (slot, created_at);
```

Колонки `slot`/`requested_model`/`fallback_reason` — nullable: старые строки остаются валидными.

### 4.2. Парсинг usage (`HttpLlmClient`)

`LlmHttpResponse` расширяется полями `cacheReadTokens`, `cacheWriteTokens`, `reasoningTokens`; в `parse` читаются:

- `usage.prompt_tokens_details.cached_tokens` → `cache_read_tokens`;
- `usage.prompt_tokens_details.cache_write_tokens` → `cache_write_tokens` (нет поля → `0`);
- `usage.completion_tokens_details.reasoning_tokens` → `reasoning_tokens`.

Отсутствие любого из полей — `0`, не ошибка.

### 4.3. Запись и стоимость (`OpenAiCompatibleLlmGateway`)

- `requested_model` = первая модель маршрута; `model` = фактически ответившая;
- `slot` = `uzelok.<step>`;
- `fallback_reason` = `NULL`, если модель первая; иначе причина (`HTTP_429`, `HTTP_5XX`, `TIMEOUT`, `TRANSPORT`, `SCHEMA_INVALID`);
- `cost()` учитывает кеш и считает `max(0, …)`; та же функция используется в `recordFailure`.

### 4.4. Таблица цен

В `uzelok.llm.pricing` добавить `cache-read-per-million`:
`opencode-go/deepseek-v4.1-flash` — 0.003, `opencode-go/claude-haiku-5-5` — 0.01, `opencode-go/gemini-4-argon` — 0.10 (источник: док-страница Go).

### 4.5. Агрегатор `~/.hermes/scripts/llm-usage-report.py`

Источники: PG `llm_call` (через `kubectl exec`), `state.db`, `opencode.db` (`$.modelID`, `$.tokens.*`, `$.cost` внутри JSON `data`), `GET /zen/go/v1/usage`.

Выводит: окна (провайдер vs локально), Drift, разбивку по сервисам и шагам, юнит-экономику ($/job, $/EXTRACT), топ-3 модели по съеденной квоте. Алерт-триггеры — по §9.3.

## 5. Требования

- **R1.** Миграция применяется на чистой и на существующей БД; старые строки читаются (`slot IS NULL`).
- **R2.** `cached_tokens` из ответа попадает в `cache_read_tokens` (тест: `prompt_tokens=1000`, `cached_tokens=800` → `cache_read=800`, `uncached=200`).
- **R3.** `cost_usd` при ненулевом кеше строго меньше, чем при той же сумме токенов без кеша.
- **R4.** Формула защищена от отрицательного `uncached_in`: при `cached_tokens > prompt_tokens` стоимость не становится отрицательной.
- **R5.** При провале контракта `cost_usd > 0` — стоимость сожжённых токенов учтена.
- **R6.** При фолбэке `requested_model ≠ model`, `fallback_reason` непустой.
- **R7.** Агрегатор не падает при недоступности источника — печатает `недоступен: <источник>` и продолжает.
- **R8.** В отчёте есть Drift; при `|Drift| > 5` — строка-алерт.
- **R9.** Юнит-экономика считается по `job_id`, включая `REGENERATE`.
- **R10.** Пиковая тарификация DeepSeek (×2, 01:00–04:00 и 06:00–10:00 UTC, Пн–Пт) учитывается в пересчёте.
- **R11.** Скрипт не печатает ключи и DSN.
- **R12.** Существующий набор тестов зелёный; новые тесты на парсинг, формулу и FAILED-строку.

## 6. DoD

1. `./gradlew cleanTest test` зелёный, число тестов и skipped указано явно.
2. `V7` применена на `uzelok_dev`, `\d llm_call` показывает новые колонки.
3. `scripts/smoke-boot.sh` — контекст стартует.
4. Живой `EXTRACT` и `DRAFT` дают строки с непустыми `slot`, `requested_model`, `cache_read_tokens`.
5. Отчёт за 7 дней печатает окна, Drift и стоимость конспекта; цифры сопоставимы с `/v1/usage`.

## 7. Вне объёма

- `PolicyDrivenLlmClient` и чтение политики внутри Uzelok;
- сетевой шлюз;
- фолбэк по нарушению контракта;
- eval, канарейки, авто-переключение моделей;
- изменение текущих моделей шагов.

## 8. Риски

- **Провайдер не отдаёт `cached_tokens`** → колонка нулевая, дрейф объясняется не кешем; проверяется одним живым вызовом с большим промптом.
- **Оценка пиковой тарификации** → допуск дрейфа 5 %.
- **Расхождение цен** между `application.yml` и каталогом моделей → сверка на этапе отчёта.
- **Рост числа колонок** при третьем провайдере → порог: больше двух провайдеров — выносим цены и лимиты в отдельную таблицу.

## 9. Факты, установленные в ходе этапа (04.11.2026)

- **Прод-база `uzelok` пуста:** `telegram_update`, `source_item`, `processing_job`, `note`, `audit_event` — по нулю строк при живом поде (Running, 39 ч). Значит ранняя версия «дрейф 15 п.п. даёт прод-бот Uzelok» **неверна**: Uzelok в расходе квоты не участвует.
- **Дрейф на 04.11:** провайдер 71 %, локально 29 % (30 дней); 45 % против 29 % на 7 днях. Причина не установлена. Версии для проверки: пиковая тарификация DeepSeek (×2), нормировка `allowance` на стороне провайдера (возможно, кеш-чтение весит как обычный вход), неучтённые сессии/инструменты на том же ключе.
- **`models-usage.py` и агрегатор расходятся** по одной и той же неделе (29 % против 56 % в старом расчёте): старый скрипт не учитывает кеш отдельной ценой. Ориентир — агрегатор.
- Подключение учёта Uzelok по-прежнему нужно, но оно **не объясняет** текущее расхождение и не должно использоваться как аргумент в отчётах, пока в базе нет трафика.
